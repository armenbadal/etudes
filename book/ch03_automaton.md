# Էտյուդ 1. Վերջավոր ավտոմատներ

Այս գրքի առաջին էտյուդում պետք է նախագծենք և իրականացնենք փոքր լեզու, որով հնարավոր կլինի նկարագրել դետերմինացված վերջավոր ավտոմատներ և դրանց օգնությամբ ճանաչել նիշերի հաջորդականություններ։

Սա դիտավորյալ պարզ խնդիր է։ Մեր առաջին նպատակը բարդ կամ հզոր ծրագրավորման լեզու ստեղծելը չէ։ Ավելի կարևոր է մեկ փոքր օրինակի վրա տեսնել լեզվի իրականացման ամբողջ ճանապարհը՝ գաղափարից մինչև աշխատող ծրագիր։ Պետք է սահմանենք լեզվի հնարավորությունները, նկարագրենք նրա շարահյուսությունը, իրականացնենք բառային ու շարահյուսական վերլուծիչներ, կառուցենք ծրագրի ներքին ներկայացումը, ստուգենք նրա իմաստային կոռեկտությունը և վերջապես կատարենք գրված ծրագիրը։

Հետագա էտյուդներում լեզուներն ու դրանց իրականացումները զգալիորեն կբարդանան, բայց այս շղթան հիմնականում նույնն է մնալու։

## Խնդիրը

Ենթադրենք ուզում ենք նկարագրել այնպիսի ավտոմատ, որը ճանաչում է `a` և `b` նիշերից կազմված մեկ կամ ավելի նիշերի հաջորդականություն, որին վերջում հաջորդում է `c` նիշը։ `ac`, `abc`, `abbc`, `abababc` հաջորդականությունները պետք է ճանաչվեն, իսկ `c`, `ab`, `cab`, `abca` հաջորդականությունները՝ ոչ։ Այդ ավտոմատը կարող ենք նկարագրել այսպես.

```text
automaton EndsWithC {
    alphabet = {'a', 'b', 'c'}
    states = {start, body, final}

    initial = start
    finals = {final}

    transitions = {
        start, 'a' -> body;
        start, 'b' -> body;
        body, 'a' -> body;
        body, 'b' -> body;
        body, 'c' -> final;
    }
}

recognize "abababc" with EndsWithC;
recognize "cab" with EndsWithC;
```

Առաջին `recognize` հրամանի արդյունքը կլինի `true`, երկրորդինը՝ `false`։ Այսպիսով՝ մեր լեզվում առայժմ կլինեն ընդամենը երկու գործողություններ՝ վերջավոր ավտոմատի սահմանում և տրված ավտոմատով նիշերի հաջորդականության ճանաչում։

Թեև լեզուն փոքր է, այն արդեն ունի ծրագրավորման լեզուներին հատուկ մի շարք հատկություններ՝ ծառայողական բառեր, անուններ, լիտերալներ, բլոկային կառուցվածք, սահմանումներ և անունների հետագա օգտագործում։ Դա բավական է լեզվի իրականացման հիմնական խնդիրների հետ առաջին անգամ ծանոթանալու համար։

## Վերջավոր ավտոմատը

Դետերմինացված վերջավոր ավտոմատը սովորաբար ներկայացվում է

\[
M=(Q,\Sigma,\delta,q_0,F)
\]

հնգյակով, որտեղ՝

- \(Q\)-ն վիճակների վերջավոր բազմությունն է,
- \(\Sigma\)-ն՝ ավտոմատի այբուբենը,
- \(\delta\)-ն՝ անցումների ֆունկցիան,
- \(q_0\)-ն՝ սկզբնական վիճակը,
- \(F\)-ը՝ վերջնական վիճակների բազմությունը։

Մեր լեզվի կառուցվածքները գրեթե ուղղակիորեն համապատասխանում են այս բաղադրիչներին.

| Ավտոմատի բաղադրիչ | Լեզվի կառուցվածք |
|---|---|
| \(\Sigma\) | `alphabet` |
| \(Q\) | `states` |
| \(q_0\) | `initial` |
| \(F\) | `finals` |
| \(\delta\) | `transitions` |

Օրինակ՝ `body, 'c' -> final;` անցումը նշանակում է, որ եթե ավտոմատը գտնվում է `body` վիճակում և կարդում է `c` նիշը, ապա պետք է անցնի `final` վիճակ։

Այս էտյուդում թույլատրենք, որ անցումների ֆունկցիան մասնակի լինի։ Եթե տվյալ վիճակի և նիշի համար անցում սահմանված չէ, ապա ավտոմատը տվյալ հաջորդականությունը չի ճանաչում։ Այդ որոշումը նկարագրությունները զգալիորեն կարճացնում է. պարտադիր չէ բացահայտ գրել բոլոր հնարավոր մերժող անցումները։

## Լեզվի մի ամբողջական օրինակ

```text
automaton Binary {
    alphabet = {'0', '1'}
    states = {even, odd}

    initial = even
    finals = {even}

    transitions = {
        even, '0' -> even;
        even, '1' -> odd;
        odd, '0' -> odd;
        odd, '1' -> even;
    }
}

recognize "101101" with Binary;
recognize "111" with Binary;
```

Այս ավտոմատը ճանաչում է այն երկուական տողերը, որոնցում `1` նիշերի քանակը զույգ է։ `Binary`, `even`, `odd` անուններն ընտրում է ծրագրի հեղինակը. դրանք **իդենտիֆիկատորներ** են։ Իսկ `automaton`, `alphabet`, `states`, `initial`, `finals`, `transitions`, `recognize`, `with` բառերը լեզվի մաս են և հատուկ նշանակություն ունեն. դրանք **ծառայողական բառեր** են։

## Լեզվի քերականությունը

Լեզվի շարահյուսությունը նկարագրենք EBNF գրառմամբ.

```ebnf
Program = { Automaton | Recognition } .

Automaton =
    "automaton" Identifier "{"
        Alphabet States Initial Finals Transitions
    "}" .

Alphabet =
    "alphabet" "=" "{" Character { "," Character } "}" .

States =
    "states" "=" "{" Identifier { "," Identifier } "}" .

Initial = "initial" "=" Identifier .

Finals =
    "finals" "=" "{" [ Identifier { "," Identifier } ] "}" .

Transitions =
    "transitions" "=" "{" { Transition } "}" .

Transition =
    Identifier "," Character "->" Identifier ";" .

Recognition =
    "recognize" String "with" Identifier ";" .
```

Առաջին տարբերակում ավտոմատի բաղադրիչների հերթականությունը ֆիքսված է։ `alphabet`, `states`, `initial`, `finals`, `transitions` բաժինները պետք է գրվեն հենց այս հերթականությամբ։ Դրանք կարելի էր թույլ տալ ցանկացած հերթականությամբ, բայց դրանից parser-ը կբարդանար՝ առանց էտյուդին էական նոր գաղափար ավելացնելու։ Առաջին խնդրում պարզությունն ավելի կարևոր է։

## Բառային միավորները

Շարահյուսական վերլուծությունից առաջ ծրագրի տեքստը պետք է բաժանել բառային միավորների՝ token-ների։ Օրինակ՝

```text
initial = start
```

տողը կարելի է ներկայացնել այսպես.

```text
INITIAL
EQUAL
IDENTIFIER("start")
```

Մեր լեզվին անհրաժեշտ են հետևյալ token-ները.

```text
IDENTIFIER  CHARACTER  STRING

AUTOMATON   ALPHABET   STATES
INITIAL     FINALS     TRANSITIONS
RECOGNIZE   WITH

LEFT_BRACE  RIGHT_BRACE  EQUAL
COMMA       SEMICOLON    ARROW

END
```

`END` token-ը նշանակում է մուտքային տեքստի ավարտը։ Իդենտիֆիկատորը կարող ենք սահմանել հետևյալ կանոնով.

```ebnf
Identifier = Letter { Letter | Digit | "_" } .
```

Այս դեպքում `state`, `state1`, `final_state`, `A0` անունները թույլատրելի են, իսկ `1state` գրառումը իդենտիֆիկատոր չէ։

Ավտոմատի այբուբենի տարրերը գրենք միակ չակերտների մեջ՝ `'a'`, `'0'`, `'+'`, իսկ `recognize` հրամանին փոխանցվող հաջորդականությունը՝ կրկնակի չակերտների մեջ՝ `"abba"`։ Առաջին տարբերակում կարելի է սահմանափակվել պարզ նիշերով և չիրականացնել escape sequence-ները։

## Բառային վերլուծիչը

Scanner-ը հերթական token-ը կարդացող բաղադրիչն է։ Նրա հիմնական գործողությունը կարելի է պատկերացնել որպես `nextToken()`։ Scanner-ը պետք է բաց թողնի whitespace նիշերը, որոշի հաջորդ token-ի տեսակը և անհրաժեշտության դեպքում պահի նաև դրա արժեքը։

Ծառայողական բառերն ու իդենտիֆիկատորները հարմար է ճանաչել նույն ճանապարհով։ Նախ կարդում ենք ամբողջ բառը, ապա ստուգում՝ արդյոք այն ծառայողական բառերի աղյուսակում կա։ Եթե կա, վերադարձնում ենք համապատասխան token-ը, հակառակ դեպքում՝ `IDENTIFIER`։

Scanner-ում արժե հենց սկզբից պահել ընթացիկ դիրքը՝ առնվազն տողի և հնարավորության դեպքում նաև սյան համարը։ Այդպես `syntax error` հաղորդագրության փոխարեն հնարավոր կլինի ստանալ, օրինակ՝

```text
line 7, column 14: expected '}'
```

## Ծրագրի ներքին ներկայացումը

Parser-ի նպատակը միայն ասելը չէ, որ ծրագիրը շարահյուսորեն ճիշտ է։ Այն պետք է կառուցի տվյալների կառուցվածք, որի հետ հետո կարող են աշխատել ծրագրի մյուս մասերը։ Այս փոքր լեզվի համար ընդհանուր նշանակության AST համակարգի կարիք դեռ չկա։ Բավական են մոտավորապես հետևյալ կառուցվածքները.

```text
Program
    automata
    recognitions

AutomatonDefinition
    name
    alphabet
    states
    initial
    finals
    transitions

Transition
    from
    symbol
    to

Recognition
    text
    automatonName
```

Այս ներկայացումը թույլ է տալիս parser-ը բաժանել ծրագրի կատարումից։ Parser-ը պատասխանատու է ծրագրի **ձևը** հասկանալու համար և չպետք է միաժամանակ զբաղվի նաև ավտոմատի կատարմամբ։

## Շարահյուսական վերլուծիչը

Մեր քերականության համար հարմար է recursive descent եղանակը։ Քերականության գրեթե յուրաքանչյուր ոչ տերմինալին կհամապատասխանի առանձին ֆունկցիա.

```text
parseProgram
parseAutomaton
parseAlphabet
parseStates
parseInitial
parseFinals
parseTransitions
parseTransition
parseRecognition
```

Օրինակ՝ `Initial = "initial" "=" Identifier .` կանոնին համապատասխան ֆունկցիայի տրամաբանությունը գրեթե բառացիորեն կլինի՝ սպասել `INITIAL`, սպասել `EQUAL`, կարդալ `IDENTIFIER` և վերադարձնել այդ անունը։ Այս ուղիղ համապատասխանությունը recursive descent parser-ի հիմնական առավելություններից է ուսումնական խնդիրներում։

Parser-ում հարմար է ունենալ ընդհանուր `match(expected)` գործողություն։ Այն ստուգում է՝ ընթացիկ token-ը սպասված տեսակն ունի՞։ Եթե այո՝ scanner-ից կարդում է հաջորդ token-ը, իսկ եթե ոչ՝ ստեղծում է շարահյուսական սխալ։ Օրինակ՝ `initial start` գրառման մեջ `INITIAL` token-ից հետո parser-ը սպասելու է `EQUAL`, բայց հանդիպելու է `IDENTIFIER`։

## Շարահյուսական և իմաստային սխալներ

`initial start` գրառումը շարահյուսորեն սխալ է, որովհետև բացակայում է `=` նշանը։ Իսկ

```text
states = {start, final}
initial = unknown
```

գրառումը շարահյուսորեն ճիշտ է, բայց `unknown` վիճակը հայտարարված չէ։ Սա արդեն **իմաստային սխալ** է։ Parser-ի աշխատանքով ծրագրի ստուգումը չի ավարտվում։

## Իմաստային վերլուծությունը

Ավտոմատի սահմանման համար պետք է ստուգել առնվազն հետևյալ կանոնները.

- ավտոմատի անունը պետք է եզակի լինի,
- վիճակների անունները պետք է եզակի լինեն,
- այբուբենի նիշերը պետք է եզակի լինեն,
- վիճակների բազմությունը չպետք է դատարկ լինի,
- սկզբնական վիճակը պետք է պատկանի վիճակների բազմությանը,
- բոլոր վերջնական վիճակները պետք է հայտարարված լինեն,
- յուրաքանչյուր անցման սկզբնական ու վերջնական վիճակները պետք է հայտարարված լինեն,
- անցման նիշը պետք է պատկանի ավտոմատի այբուբենին,
- նույն `(վիճակ, նիշ)` զույգի համար պետք է լինի առավելագույնը մեկ անցում,
- `recognize` հրամանում օգտագործվող ավտոմատը պետք է սահմանված լինի։

Կրկնությունները ստուգելու համար parser-ը չպետք է կարդացած անուններն անմիջապես պահի `set` կառուցվածքի մեջ և այդպիսով լուռ վերացնի դրանք։ Ծրագրի ներքին ներկայացումը սկզբում պետք է հնարավորինս պահպանի այն, ինչ գրել է հեղինակը։ Կրկնությունը սխալ համարելը semantic analyzer-ի գործն է։

Դետերմինացվածության կանոնը հատկապես կարևոր է։ Նույն վիճակի և նույն նիշի համար չի կարելի երկու տարբեր անցում սահմանել.

```text
start, 'a' -> left;
start, 'a' -> right;
```

Այստեղ արդեն ստուգում ենք ոչ միայն անունների գոյությունը, այլև ավտոմատի մաթեմատիկական հատկությունը։

## Ծրագրի կատարումը

Եթե ծրագիրն անցել է շարահյուսական և իմաստային ստուգումները, կարելի է այն կատարել։ Ավտոմատի աշխատանքի ալգորիթմը շատ պարզ է.

```text
state = initial

for symbol in input:
    transition = delta(state, symbol)

    if transition does not exist:
        return false

    state = transition.to

return state is final
```

Բուն interpreter-ը կարող է շատ փոքր լինել։ Սա առաջին էտյուդի կարևոր արդյունքներից մեկն է. լեզվի իրականացման աշխատանքի մեծ մասը կատարվում է մինչև կատարման փուլ հասնելը։ Անհրաժեշտ է հասկանալ ծրագրի տեքստը, կառուցել նրա ներկայացումը և ստուգել սահմանումների կոռեկտությունը։ Բուն ավտոմատի կատարումը դրանց համեմատ պարզ է։

Անցումները կարելի է պահել ցուցակով և յուրաքանչյուր քայլի ժամանակ հերթով փնտրել համապատասխան անցումը։ Առաջին իրականացման համար դա բավարար է։ Հետագայում կարելի է կառուցել `(state, symbol) -> nextState` աղյուսակ, որպեսզի `delta` գործողությունը դառնա ուղղակի որոնում ըստ զույգ բանալու։

## Սխալների հաղորդագրությունները

Սխալ հայտնաբերելը աշխատանքի միայն կեսն է։ Անհրաժեշտ է նաև օգտվողին բացատրել, թե ինչն է սխալ։ `semantic error` հաղորդագրության փոխարեն կարելի է գրել.

```text
line 6: initial state 'begin' is not declared
```

կամ՝

```text
line 12: transition uses symbol 'c',
which is not in the automaton alphabet
```

Հնարավորության դեպքում սխալի հետ պետք է պահել նաև սկզբնական ծրագրում համապատասխան կառուցվածքի դիրքը։ Դա նշանակում է, որ token-ների հետ միայն նրանց արժեքը պահելը միշտ բավարար չէ։

## Թեստավորում

Լեզվի իրականացումը պետք է փորձարկել ոչ միայն ճիշտ ծրագրերով։ Անհրաժեշտ են առնվազն երեք տեսակի թեստեր։

**Բառային վերլուծության թեստերը** պետք է ստուգեն ճիշտ token-ների հաջորդականությունը, ինչպես նաև սխալ նիշերը, չփակված տողերն ու նիշային լիտերալները։

**Շարահյուսական թեստերը** պետք է տարբերեն, օրինակ, `initial = start` և `initial start` գրառումները՝ ընդունելով առաջինը և մերժելով երկրորդը։

**Իմաստային թեստերը** պետք է առանձին օրինակ ունենան յուրաքանչյուր կանոնի համար՝ չհայտարարված սկզբնական կամ վերջնական վիճակ, անհայտ վիճակ անցման մեջ, այբուբենին չպատկանող նիշ, կրկնվող վիճակ, ոչ դետերմինացված անցումներ և գոյություն չունեցող ավտոմատի օգտագործում։

Վերջապես պետք է փորձարկել նաև ավտոմատի իրական աշխատանքը։ Առնվազն մեկ ավտոմատի համար ցանկալի է կազմել ճանաչվող և չճանաչվող տողերի բավական մեծ հավաքածու։

## AI գործիքների օգտագործումը

Այս խնդիրը կարելի է ամբողջությամբ հանձնարարել AI գործիքին և արագ ստանալ աշխատող թվացող scanner, parser և interpreter։ Սակայն այս գրքի նպատակի տեսանկյունից դա առանձնապես օգտակար չէ։ AI-ին կարելի է հանձնարարել լրացուցիչ թեստային օրինակների և սխալ ծրագրերի գեներացում, scanner-ի սահմանային դեպքերի վերանայում, unit test-ների սկզբնական կմախքի կառուցում կամ սխալների ավելի օգտակար հաղորդագրությունների առաջարկում։

Լեզվի քերականությունը, իմաստային կանոնները և ծրագրի ներքին ներկայացումը ցանկալի է սկզբում նախագծել ինքնուրույն։ AI-ի գեներացրած կոդը նույնպես պետք է դիտարկել որպես ստուգման ենթակա կոդ։ Կարելի է, օրինակ, նրան տալ ավտոմատի կատարման մի իրականացում և խնդրել գտնել այնպիսի մուտքեր, որոնց դեպքում կոդը սխալ արդյունք է տալիս կամ վթարվում է, ապա ստուգել նաև այն դեպքերը, որոնք AI-ն բաց է թողել։

## Ինքնուրույն աշխատանք

Իրականացրեք այս գլխում սահմանված լեզուն։ Ծրագիրը պետք է կարողանա՝

1. կարդալ լեզվով գրված ծրագիր,
2. կատարել բառային վերլուծություն,
3. կատարել շարահյուսական վերլուծություն,
4. կառուցել ծրագրի ներքին ներկայացումը,
5. կատարել իմաստային ստուգումներ,
6. կատարել `recognize` հրամանները։

Սխալների հաղորդագրություններում հնարավորության դեպքում նշեք սկզբնական ծրագրի համապատասխան տողն ու սյունը։

## Լրացուցիչ առաջադրանքներ

1. **Մերժող վիճակ։** Մասնակի անցումների փոխարեն պահանջեք, որ անցումների ֆունկցիան ամբողջական լինի, կամ ավտոմատ կերպով ավելացրեք հատուկ մերժող վիճակ և բացակայող բոլոր անցումները ուղղեք դեպի այն։
2. **Դատարկ տողի ճանաչում։** Կազմեք ավտոմատ, որը ճանաչում է դատարկ տողը, և ստուգեք՝ interpreter-ը ճիշտ աշխատո՞ւմ է զրոյական երկարությամբ մուտքի համար։
3. **Գրաֆիկական ներկայացում։** Ավտոմատի նկարագրությունից գեներացրեք Graphviz DOT ֆայլ։ Այս դեպքում նույն ներքին ներկայացումը կօգտագործեն և՛ interpreter-ը, և՛ DOT գեներատորը։
4. **Բաժինների ազատ հերթականություն։** Թույլատրեք `alphabet`, `states`, `initial`, `finals`, `transitions` բաժինները գրել ցանկացած հերթականությամբ։ Որոշեք՝ ինչ անել, եթե մի բաժին բացակայում է կամ գրված է երկու անգամ։
5. **Ավտոմատների համեմատություն։** Ավելացրեք հրաման, որը նույն տողը ճանաչում է երկու տարբեր ավտոմատներով։ Սա կարող է բերել ավելի բարդ խնդրի՝ երկու վերջավոր ավտոմատների համարժեքության ստուգմանը։

## Ինչ ստացանք

Այս էտյուդում մենք դեռ չենք կառուցել ընդհանուր նշանակության ծրագրավորման լեզու։ Չունենք թվաբանական արտահայտություններ, փոփոխականներ, պայմանական հրամաններ կամ ֆունկցիաներ։ Բայց արդեն իրականացրել ենք ծրագրավորման լեզվի գրեթե ամբողջ հիմնական շղթան.

```text
source text
    ↓
scanner
    ↓
tokens
    ↓
parser
    ↓
program representation
    ↓
semantic analysis
    ↓
execution
```

Հետագա էտյուդներում այս սխեման նորից ու նորից կհանդիպի մեզ։ Կփոխվեն լեզուները, կբարդանան դրանց կառուցվածքները, կհայտնվեն արտահայտություններ, տիպեր, անունների տեսանելիության տիրույթներ և կոդի գեներացիա։

Բայց առաջին և ամենակարևոր քայլն արդեն արված է. մենք վերցրինք փոքր խնդրային տիրույթ, դրա համար նախագծեցինք լեզու և այդ լեզվի նկարագրությունը վերածեցինք աշխատող համակարգի։
